# 首次点名资源准备

## 本次边界

在现有 `src/` → `npm run build` → `dist/` 生产流程内优化。保留星空球体、翻牌画面、系统减少动态效果下的核心动画、随机选择、班级/点名会话及所有既定时间戳。没有变更动画时钟、补帧逻辑、画质控制器、发布流程、EXE 或部署。星空渲染器文件逐字节保持基线不变。

首次翻牌原来会依次 `start` 和 `prepare`，同一点击绘制两遍；现在由 `prepare` 直接开始完整的 600 ms 翻牌，只有一遍同步绘制。

## 资源准备策略

- 页面完成正常启动后才排入空闲任务，不增加“必须预热完成”的启动等待或点名禁用状态。
- 本机字体通过 FontFaceSet 提前请求；不新增远程字体来源。字体失败使用原来的系统回退字体。
- 仅在翻牌主题提前准备纸牌通用正反面、阴影、布局与背景。只保留原来的单个选中姓名画布，不预画整班的高分辨率姓名卡。
- 星空保持原有资源路径，不新增预热任务、隐藏纸牌画布或人物缓存。它的 atlas 已在普通待机中加载/渲染；没有可验证收益的额外 GPU 预热已撤回。教室可用时通过原 Three 的 compileAsync 提前准备本场景材质，不向共享画布绘制。
- 人物只在教室主题准备。最多两种共享男女基础定义的原有 25 姿态缓存，以及两个共享 hero 定义的坐/立端点；hero 的 23 个中间姿态仍按需构建。不会为每个学生创建一个精模，也不预热教师。
- 下载、JSON 解码、Three 解析、坐姿编译与站姿编译分别处理。下载 Promise 完成只缓存数据，不会自动连着执行整套重活。
- 每个空闲回调最多处理一个资源。没有足够空闲时间、正在点名/倒计时或页面隐藏时，至少 80 ms 后再检查，避免忙循环。换班或切主题会换 generation 并取消未开始的旧任务。
- 4 ms 是开始任务所需的剩余空闲时间门槛，绝不是单任务最大耗时保证。一个不可再拆的姿态烘焙仍可能超过一帧；低配置设备实际效果尚需验证。提前点击安全地走原有按需路径，预热不会推迟抽取截止时间。

## 内存代价（实际模型，去重 geometry ArrayBuffer）

| 路径 | 初始 | 准备后 | 新增 |
| --- | ---: | ---: | ---: |
| 完整模型 | 500,448 B | 17,146,308 B | 16,645,860 B（15.87 MiB） |
| software 模型 | 201,840 B | 5,739,792 B | 5,537,952 B（5.28 MiB） |

这些数字只包含共享 geometry 缓冲区，不包含解析对象、字体、浏览器或驱动内存。完整模型准备后测试上界为 20 MiB；software 为 16 MiB。使用者之后实际进行不同动作时，原来的按需缓存仍可能增长。曾评估的“全部 hero 中间姿态预热”需要新增约 57 MiB，已舍弃。

本云 CPU 的一次分项测量：基础姿态最长 21.7 ms，拆分后的 hero 单项最长 17.4 ms。不同运行存在噪声，不将它们当作低配置 Windows 的上界。

## 可复现测量与限制

基线是 main `6575f42cda114bdff6fae9318b5260efdb1a05d0`。两版均先执行 `node scripts/build.mjs`，再用同一份脚本：

```sh
node tests/helpers/profile-first-draw.mjs /absolute/path/to/built/repo classroom
node tests/helpers/profile-first-draw.mjs /absolute/path/to/built/repo space
node tests/helpers/profile-first-draw.mjs /absolute/path/to/built/repo paper
```

每次独立 Node 进程，64 个合成姓名，1366×768，先经过相同的 6 秒、60 Hz 模拟空闲窗口，再执行第一次点名和 64 个 50 ms 推进帧。使用真实 `dist/scene.js`、模型和绘制逻辑；DOM/Canvas/音频与动画时钟使用既有确定性夹具，`node:perf_hooks` 计量这段 JS 工作负载的墙钟耗时（含宿主调度影响），`process.cpuUsage` 另记进程级 CPU 时间。每个主题进行 5 组按基线→修改版顺序的配对运行。

这不是浏览器 FPS、像素、音频或 GPU 测试。夹具 DOM 与真实浏览器的代价不同，Canvas 不真正栅格化，不能用这些数字宣称 Windows 卡顿已经消失。当前云端独立 Chromium 被执行器 socket/mount 限制阻止，另一个云浏览器不能访问此本地预览；没有绕过限制或使用用户电脑。真实 Windows GPU、低端设备及立即点击仍需人工性能验收。

下方测量结果及全部逐次数据随本 PR 保存。结构上可稳定验证的收益是：首次翻牌点击绘制次数 2→1；准备完成的基础人物起立不再现场烘焙新姿态；预热本身不抽随机姓名、不改已用名单、不额外启动 RAF。

首次尝试统一准备所有主题，会在星空主题额外建立约7MiB隐藏翻牌画布。CPU对照中观察到退化，已撤回这条无可证收益的路径；最终版本的星空没有新的资源准备任务。

### 最终收窄版本的测量

以下为 5 组配对运行的中位数，单位 ms。原始值含所有离群点，见 `first-draw-cpu-samples.json`。

| 主题 | 首次点击同步耗时，前→后 | 首次动画帧 P95，前→后 |
| --- | ---: | ---: |
| 教室 | 12.56 → 14.86 | 6.37 → 3.70 |
| 翻牌 | 28.16 → 18.33 | 3.47 → 4.74 |
| 星空（未优化） | 8.05 → 7.75 | 4.68 → 5.35 |

课堂的主要实测收益在起立动画途中：原来首次点名会新增人物姿态，现在所需基础姿态已经存在。点击同步耗时并未证明改善。翻牌的稳定收益是移除一次重复绘制；本轮点击中位数降低，但修改版单次出现 120.51 ms 离群值，不能宣称没有卡顿或整体帧性能改善。

星空另用 10 组交替 AB/BA 顺序核查：首次点击中位数 9.02 → 9.48 ms，范围 6.82–23.05 → 7.02–18.31 ms；帧 P95 中位数 5.61 → 6.48 ms，范围 4.60–12.68 → 4.27–12.32 ms。样本波动很大，不宣称星空提速；额外的 `space.start` 分段为 4.14 → 4.09 ms。分段 wrapper 在每次点击后立即恢复，不混入第二次点名。隔离测试验证无新增字体任务、隐藏纸牌资源、人物姿态预热或随机抽取，两个星空源文件保持不变。
